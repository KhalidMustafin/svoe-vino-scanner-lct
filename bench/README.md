# Стенд замеров OCR

Стенд меряет одного читателя этикетки на одном наборе с одним режимом кропа. OCR здесь
не выбирает вино: текстовый top-1 — только диагностика, решение принимает resolve
поверх кандидатов CV. Когда появится CV, в предсказаниях будут `cv_top5` и `final_top5`,
и `bench.metrics` посчитает сравнение «CV» против «CV+OCR».

## Наборы

| Набор | Откуда | split | Для чего |
|---|---|---|---|
| `public` | `$SVS_DATASET_DIR/eval/queries` и `queries.tsv` + разметка `data/gt/public_gt.tsv`, `data/gt/public_annotations.jsonl` | `smoke` | только дымовой тест |
| `synth` | `data/raw/synth/` (`synth_manifest.tsv`, `synth_gt.tsv`, `synth_annotations.jsonl`) | dev/test по хэшу | регрессия геометрии: соседи, ценник, наклон |
| `manifest` | полевой набор: `query_id<TAB>image_path` (как `participant_test.sh`) + эталон `query_id<TAB>slug\|__none__[<TAB>in_catalog][<TAB>split]` + JSONL разметки | dev/test | решения |

Эталонные токены каталога ожидаются в `data/gt/gt_tokens.jsonl` (`--gt-tokens`).
CER считается по ручной транскрипции кадра (`front_label_text`), а если её нет — по
первичным токенам каталога (`expected_tokens`).

## Сплиты

- dev 40 % / test 60 %. Разбиение задаёт sha256 от группы двойников уровня B
  (`cluster_B` в `gt_tokens.jsonl`), а для slug вне групп — от slug. Все кадры одной
  бутылки и все её двойники попадают в один split и не зависят от порядка строк. Без
  `gt_tokens.jsonl` группы неизвестны, и делится по slug.
- Кадры вне каталога делятся по `bottle_id` из разметки, а без него — по `query_id`.
- Колонка `split` в эталоне перекрывает хэш: там задаётся стратифицированное
  разбиение полевого набора. Двойники, разошедшиеся по dev и test, `--dry-run` показывает в
  `cluster_conflicts` и не пропускает.
- Пороги, веса и словарь подбираются только на dev. Прогон без `--split` идёт по dev
  (`public` — по smoke). Test запускают один раз, для отчёта, явным `--split test`.
  `--dry-run` без `--split` проверяет весь набор.
- `--split all` (и у `bench.ocr_bench`, и у `bench.retrieval`) нужен ради предсказаний по
  всему набору: это вход `bench.train_resolve --final-test`. Метрики test у такого прогона
  запечатаны: `metrics.json` и вывод в консоль посчитаны без кадров test (`sealed_test`
  говорит, сколько кадров спрятано и где), а метрики всего набора вместе с test лежат в
  конверте `metrics.test-sealed.json`. Конверт открывают один раз, для итогового отчёта.
  `--unseal-test` снимает печать явно — не для прогонов, которые идут в обучение. У
  прогонов `runs/cvall-*` и `runs/ocr-*`, сделанных до печати, старый `metrics.json`
  перенесён в конверт целиком, а на его месте — паспорт прогона и блоки dev.

**Правило:** публичные кадры (q1–q3) — только дымовой тест. Параметры по ним не подбираются,
а правила под их строки («1894», «25.09.25», «24 месяца») не пишутся. Ловушки описываются
общими правилами и проверяются синтетическими строками.

## Запуск

```bash
# проверить набор без читателя: файлы, эталон, согласованность split
python -m bench.ocr_bench --dataset synth --dry-run
python -m bench.ocr_bench --dataset manifest --manifest field_manifest.tsv \
    --gt field_gt.tsv --ann field_annotations.jsonl --dry-run

# один прогон: читатели, кроп и размер фиксированы
python -m bench.ocr_bench --dataset public --reader vlm:qwen3-vl:4b-instruct \
    --crop full --crop-px 1024 --out runs/vlm4b-full-1024/
python -m bench.ocr_bench --dataset synth --reader vlm --reader easyocr \
    --crop label --target annotation --out runs/vlm-easyocr-label/

# метрики по готовым предсказаниям и самопроверка кода метрик
python -m bench.metrics --gt synth_gt.tsv --ann synth_annotations.jsonl --pred p.jsonl
python -m bench.metrics --gt synth_gt.tsv --ann synth_annotations.jsonl --selftest

# синтетика (только CPU; пути ко входам — аргументами)
python -m bench.synth.make_field_synth --n 12 --out data/raw/synth \
    --photo-stats photo_stats.jsonl --photo-map slug_photo_map.csv \
    --gt-tokens data/gt/gt_tokens.jsonl --clusters near_dup_clusters.json
```

Кадр идёт тем же путём, что в сервисе: `decode_image` → рамка цели → `read_label`
(кроп, читатели по очереди с общим `--budget-ms`, токены, словарь, поля). Бюджет по
умолчанию — сервисный (`pipeline.DEFAULT_BUDGET_MS`, 2 500 мс). С бюджетом больше в
`metrics.json` стоит `run.sla_budget: false`: статусы timeout и `budget_exceeded` у такого
прогона не такие, как в сервисе. До цикла по кадрам стенд прогревает читателей
(`--warmup`, включён по умолчанию; `--no-warmup` выключает). Каждый читатель читает
синтетический кадр размера `--crop-px` с бюджетом 60 с, мимо кэша чтений. Без прогрева
первый кадр упирается в бюджет из-за холодной загрузки модели, а timeout не кэшируется.
Модель зрения держится в памяти Ollama 30 минут (`keep_alive`). Словарь берётся из
`--lexicon` (по умолчанию `data/index/lexicon.json`). Если файла нет, стенд предупреждает и
заполняет только поля по правилам: год, сахар, крепость, серию, цвет. `--no-lexicon`
отключает словарь явно.

Прогон пишет в `--out`:
- `predictions.jsonl` — строка на кадр:
  - `query_id`, ключ первого чтения `reader`, все чтения `readers`, `status` (ok, если
    хоть одно чтение ok);
  - `raw_text`, `raw`, `lines`, `latency_ms` (сумма по чтениям), `prompt_tokens`, `timings_ms`
    по шагам;
  - `crop_used` (что реально прочитано), `degraded`;
  - `fields` — плоские поля для `bench.metrics`, `label_fields` — полный `LabelFields`;
  - `text_top5` и `text_top5_scores` — **диагностика**: slug из попаданий словаря,
    взвешенные idf. Это не ответ сканера: вино выбирает resolve поверх CV.
- `metrics.json`:
  - CER ключевых токенов по полям и split;
  - статусы и флаги `degraded`;
  - доля кадров с заполненным полем (`fields_filled`) и точность полей против
    `gt_tokens` (`field_accuracy`). Оговорки лежат в `field_accuracy_notes`: часть «сорт»
    в `cuvee_or_grape` цикличная, потому что эталон и парсер берут одну таблицу
    `GRAPE_SYNONYMS`. Ошибка самой таблицы этой метрикой не видна, пока часть эталона не
    проверена глазами;
  - p50 и p95 задержки (`latency_ms_warm` — без первого кадра);
  - `run.warmup` — прогрев по читателям: статус и `elapsed_ms`. В задержку кадров и
    `run.wall_s` он не входит; при `--no-warmup` значение `null`;
  - `diagnostic_text_only` — только со словарём;
  - параметры прогона.

Кропы `bottle`, `label` и `band` строит `read_label` по рамке цели. Рамку задаёт `--target`:
- `annotation` (по умолчанию) — рамка бутылки из разметки кадра (`target_bbox_visible`),
  считается надёжной. Это оракул: он меряет читателя, а не выбор бутылки. У публичных кадров
  рамок нет, поэтому `--dry-run` с таким кропом их не пропустит. Кадр без рамки в прогоне
  читается целиком, с флагом `crop_fallback_full`.
- `detector` — детектор бутылок CV (`app.detect.bottles`). Ему нужны веса torchvision и
  видеокарта, а ненадёжная рамка тоже даёт весь кадр.

`full` — весь кадр с длинной стороной `--crop-px`, рамка не нужна.

Существующий прогон не перезаписывается без `--overwrite`. Чтения идут через кэш
(`CachedReader`, по умолчанию `<SVS_CACHE_DIR>/readings`), поэтому метрики пересчитываются
без GPU.

Коды выхода `ocr_bench`:
- 0 — готово;
- 1 — набор не прошёл проверку;
- 2 — ошибка аргументов или набора;
- 3 — конвейер, словарь или читатель не готовы.

Несколько `--reader` читаются по очереди внутри кадра. Правило «одна модель на карте» это
не отменяет: VLM в Ollama и EasyOCR на GPU вместе — две GPU-задачи.

## GPU: строго по одной задаче

- Одна задача на карте за раз: один процесс `ocr_bench`, одна модель. Больше двух
  GPU-задач сразу дают CUDA OOM, «@@@@» и зависания.
- Внутри прогона кадры идут последовательно, без потоков и повторов.
- Перед задачей проверьте, что `ollama ps` пуст, и выставьте `CUDA_VISIBLE_DEVICES` явно.
  После задачи с Ollama выгрузите модель (`keep_alive: 0`): сама она держится 30 минут.
- Если модель выдала «@@@@» или зависла, остановите очередь и перезапустите Ollama вручную.
- Тесты стенда работают только на CPU. Тесты, которым нужна карта или модель, запускаются
  лишь при `SVS_RUN_GPU_TESTS=1`.

## Обучаемый resolve (`bench.train_resolve`)

Ручной `app.resolve.rerank` с полями VLM на `pairs` исправлял 8 ответов CV и ломал 14: текст
перебивал уверенную картинку (чужая винодельня при отрыве 0,06–0,11), а внутри винодельни
путал соседние позиции линейки («Мускат» — «Мускат Чёрный», «Южная вертикаль» — «…
премиум»). Обучаемый resolve заменяет ручные веса логистической регрессией поверх тех же
кандидатов top-K CV. Всё на CPU, по готовым прогонам `bench.retrieval` и `bench.ocr_bench`.
Штраф за «лишние» слова названия пробовали и убрали: читатель недочитывает этикетку, и
штраф ломал верные длинные названия чаще, чем чинил короткие (см. замер ниже).

| Файл | Что делает |
|---|---|
| `app/resolve/features.py` | признаки пары «запрос — кандидат»: `pair_features(query_cv, fields, cand_slug, attrs, *, raw_text=None)` и `query_features(query_cv, reads, attrs, *, top_k, options)` |
| `app/resolve/learned.py` | `LogisticRanker(names, *, l2, loss, signs)`: L2-логистическая регрессия на numpy (проекционный Ньютон, знаки весов держатся), argmax внутри запроса, softmax с температурой, JSON; `rank_query(model, query_cv, reads, attrs)` → `LearnedRanking(slugs, scores, p_top1)` — вызов для сервиса. Читателя модели нет в `reads` (сбой OCR) — чтение пустое, решает CV |
| `bench/train_resolve.py` | CLI: групповая K-fold по `cluster_B`, вложенный выбор L2, отчёт out-of-fold, модели, `--final-test` |

### Признаки

Только из входа сервиса: выдача CV, `LabelFields` и сырой текст читателя, таблица каталога.
Эталонный slug функции не получают; поле `slug` в записи прогона не читается (тест подменяет
его и сверяет признаки). Всё относительное считается внутри кандидатов того же запроса;
средние и σ для стандартизации — в `LogisticRanker.fit` по обучающим парам.

Счёт линейный, ответ — argmax внутри запроса. Признак, одинаковый у всех кандидатов запроса
(«текст пустой», доля прочитанных полей, отрыв top-1 сам по себе), на ответ не влияет, поэтому
таких нет; отрыв входит только взаимодействием «отрыв × это top-1». У согласия нет столбца «не
прочитано»: он линейно зависел от двух других и константы, и L2 делил вес между ними. Базовый
уровень — «не прочитано», и сырой вес `*_match` / `*_conflict` — сразу сдвиг счёта против него.

| Группа | Признаки | Знак веса |
|---|---|---|
| `cv` | счёт, ранг, 1/ранг, счёт − top-1, z и min-max в выдаче, «это CV-top1», отрыв top-1 × «это top-1» | свободен |
| `cv_group` | log размера `visual_group` и `cluster_B` кандидата, «двойник / сосед по линейке CV-top1» | свободен |
| `winery` | согласие / противоречие (`rerank.agreement`), они же × уверенность чтения | ≥ 0 / ≤ 0 |
| `winery_text` | доля слов названия винодельни кандидата в сыром тексте; 1/df самого редкого прочитанного её слова | ≥ 0 |
| `grape`, `sugar`, `year`, `serial`, `color`, `abv`, `cuvee` | согласие / противоречие; год — только у карточек с годом | ≥ 0 / ≤ 0 |
| `name` | сколько значимых слов названия кандидата найдено (потолок 3); то же минус лучший кандидат запроса | ≥ 0 |
| `published` | карточка не опубликована; выключено, включается `--published` | свободен |

Знаки держит обучение (`features.feature_sign`, проекционный Ньютон): согласие не может
снижать счёт, противоречие — повышать. Без этого на 298 запросах модель выучивала шум вроде
«противоречие по сахару повышает счёт». `--free-signs` снимает ограничение — только для
сравнения.

`name` — только положительная сторона: слово названия, которого читатель не прочёл, кандидата
не штрафует. Штраф за «лишние» слова ломал верные длинные названия, недочитанные OCR
(«Совиньон Блан. Авторская технология. Моно» → «Совиньон Блан»). Слова названия — без фраз
сорта, сахара, цвета и серии словаря (их сравнивают свои группы с канонизацией: «reserve» от
«резерв» — две правки, сырым словом не найти), без слов сахара и типа в любом роде («Мускат
Сухой», «игристый», опечатка «полсусладкое»), без общих слов (`GENERIC_WORDS`,
`LABEL_GENERIC`) и без названия винодельни в любом написании. Бренды линеек («ДНК. Аллели»)
остаются: ими позиции одной винодельни и различаются. Русское прилагательное цвета остаётся
словом названия, когда отличает позицию от соседей по линейке: последнее слово названия сорта,
если сорт в каталоге встречается с разными цветами («Мускат белый» — «Мускат розовый» —
«Мускат янтарный»; у «Кокур белый», «Цимлянский чёрный», «Одесский чёрный» цвет один, и сорт
сравнивает группа `grape`), и цвет в роде сорта или стиля сразу после него («Мускат Чёрный»,
«Мускатель белый», «Портвейн красный»). В прочих местах и в среднем роде это цвет вина («Купаж
красный», «Портвейн - белое креплёное»), его сравнивает группа `color`. Цвет ищется без
правки, в любом роде и числе, кроме среднего: «белый» названия находится в «БЕЛЫЙ» и «белая»,
но не в «вино белое» — цвет вина уже сравнивает группа `color` (`features.name_word_found`).
Остальные слова считаются прочитанными при совпадении нормы, скелета транслитерации или скелета
с одной правкой (от пяти букв).

Текстовые признаки каждого читателя идут с префиксом `читатель.`: модель `vlm35` ждёт чтение
под ключом `vlm35`. Версия набора признаков — `FEATURE_VERSION` (сейчас
`resolve-features/3`); модель другой версии не загружается. Версия меняется и при правке
разбора полей этикетки (`app/reading/fields.py`, `taxonomy.py`): признаки считаются из полей.
`resolve-features/3` — поля после правки родов цвета и сахара; модели на `/2` (в том числе
`configs/resolve/s2so400m-vlm35.json` итогового замера) с нынешним кодом не загружаются.

### Протокол

```bash
python -m bench.train_resolve \
    --cv runs/cvall-s2so400m-pairs/predictions.jsonl \
    --cv runs/cvall-s2so400m-pairs_phone/predictions.jsonl \
    --ocr vlm35:pairs=runs/ocr-pairs-vlm35/predictions.jsonl \
    --ocr vlm35:pairs_phone=runs/ocr-pairsphone-vlm35/predictions.jsonl \
    --ocr rapid:pairs=runs/ocr-pairs-rapid/predictions.jsonl \
    --ocr rapid:pairs_phone=runs/ocr-pairsphone-rapid/predictions.jsonl \
    --split dev --folds 5 --top-k 20 --out runs/resolve-s2so400m/
```

- Прогон OCR привязан к набору явно: `--ocr читатель:набор=путь`. У `pairs` и `pairs_phone`
  одинаковые `query_id` и эталоны, поэтому ключ — пара «`meta.set` + `query_id`». Запись OCR
  сверяется с запросом CV: эталон, половина (`split`) и кадр. Порченый запрос
  (`meta.phone_seed`) CV ищет по исходному снимку, а OCR читает сохранённую порченую копию,
  поэтому путь кадра OCR у `pairs_phone` обязан отличаться от пути CV, а у `pairs` — совпадать.
  Перепутанные файлы двух наборов — ошибка данных.
- Половина — как у `bench.retrieval.assign_splits`: `meta.split`, без него — `split_for` по
  `cluster_B`. У `pairs*` объявленная половина сверяется с хэшем. Строка чужой половины
  декодируется как JSON (без этого не узнать `slug`), но из неё берутся только `query_id`,
  `slug` и `meta`: кандидаты, поля этикетки и признаки не читаются.
- Кандидаты — top-K CV. Если верного slug в top-K нет, запрос не входит в обучение. В
  отчёте он остаётся промахом, а его доля видна в колонке «потолок K».
- Фолды групповые: ключ — `cluster_B` эталона, вне кластеров — slug. Кадр из `pairs` и его
  порченая копия из `pairs_phone` всегда в одном фолде.
- Out-of-fold — вложенный. В каждом внешнем фолде функция потерь (`pointwise` — по парам,
  `listwise` — softmax по запросу) и L2 выбираются внутренней групповой K-fold на остальных
  фолдах. Критерий — средняя по фолдам точность top-1, при равенстве — меньший NLL верного.
  Там же, по внутренним out-of-fold счётам, подбирается температура. Цифры «обученный» этим
  выбором не подсмотрены.
- С `--select-groups` внутри того же выбора работает обратное исключение групп признаков. Это
  долго: десятки минут на вариант.
- Модель для сервиса обучается на всём dev. Гиперпараметры выбираются обычной K-fold на всём
  dev (таблица сетки), температура — по её out-of-fold счётам.
- «Ручной rerank» — `rerank` с `DEFAULT_CONFIG` и тем же `top_k`, как `bench.retrieval
  --with-ocr`. Цифры CV и ручного rerank совпадают с прогонами `runs/cvocr-*`.
- Варианты: имя читателя, `both` и `none`. `both` даёт признаки всех читателей с
  префиксами, а ручной rerank получает поля, слитые по порядку `--ocr`. `none` — обучаемый
  реранк только по CV: он отделяет вклад текста от вклада обучения.
- Ничьи CV. У визуальных двойников счёт top-1 и top-2 бывает равен до бита (например, Бюрне
  «Вионье» и «Пино Блан»). CV-top1 там — порядок файла, ручной rerank при равном счёте берёт
  меньший slug, и «исправил / сломал» на таком запросе — жребий. Колонка «ничьи CV» считает
  такие запросы, «(н. +a/−b)» — сколько исправлений и поломок пришлось на них, а в скобках у
  «CV top1» — честная доля (1/k, если эталон среди k равных). В `oof_predictions.jsonl` —
  `cv_tie_k`.
- Веса одного столбца между группами не сравнимы: у винодельни совпадение разложено на
  `winery_match` и `winery_match_conf` (корреляция 0,97). Таблица «Контрасты групп» в
  `tables.md` складывает их (при уверенности 1): это вклад группы в счёт.

В `--out` пишутся:
- `metrics.json`: `test_used`; паспорт прогона с sha1 входов; по вариантам — `oof` (по наборам
  и `all`: n, потолок K, top-1/top-5 трёх колонок, «исправил / сломал» относительно CV,
  ничьи CV `cv_ties`, `cv_only.top1_tie_fair`, калибровка по децилям, выбор во внешних
  фолдах), `selection` (сетка на всём dev), `model` (веса по убыванию |w|, `contrasts` —
  контрасты групп, `fit_info.status` — `converged`, `line_search_failed` или `max_iter`,
  сколько весов на границе знака); `run.signed` — держались ли знаки;
- `oof_predictions.jsonl`: строка на запрос и вариант, с `why_not_cv_top1` — группами
  признаков, поднявшими ответ над CV-top1, и `cv_tie_k`;
- `models/<вариант>.json`;
- `tables.md` — те же таблицы, что в stdout.

`--final-test` по умолчанию выключен. С ним после всего сказанного читается test, и модели,
обученные на всём dev, оцениваются на нём один раз с теми же колонками. В `metrics.json`
тогда стоят `"test_used": true` и `test_warning`, рядом пишется `test_predictions.jsonl`. Без
флага из строк test берутся только `query_id`, `slug` и `meta`. Тест кладёт в test-строки заведомо битые
кандидаты и поля: прогон без флага проходит, прогон с флагом падает.

Рядом с цифрой test `--final-test` называет `cross_split_twins`: пары «dev — test» с одной
основой `query_id` без года, чьи эталоны лежат в разных `cluster_B`. `cluster_B` не
объединяет один продукт разных лет, и одна такая пара уже известна: «Новый Свет. Пино Нуар»
брют розовое 2018 (test, `cluster_B` 87, «Игристое вино выдержанное…») и 2020 (dev,
`cluster_B` 2, «Российское шампанское коллекционное…»). Разбиение не меняется — оно общее со
стендом поиска. Это один запрос из 209, но о нём надо сказать рядом с цифрой test.
