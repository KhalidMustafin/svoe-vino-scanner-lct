## `s2so400m-vlm35-goal.json` — модель прежнего пути (`SVS_CANDIDATE=off`)

Копия `runs/goal/iter20/resolve/models/vlm35.json` байт в байт (sha1
`be51adb713e1b7b7b564a41c73dce384066d22be`): модель на всём dev из `bench.train_resolve
--variants vlm35 --split dev --folds 5 --top-k 20`. Формат, признаки, читатель, словарь и поля
этикетки — те же, что у `-m2`. Другое одно: счёты CV, на которых она училась и которые ей
передаёт сервис.

**Агрегация CV `per_slug="zmax"`** (`app.features.index.align_pairs`, константа `CV_PER_SLUG`
в `app/api/config.py`). У каждой пары «окно запроса w × вид эталона v» (4 × 3) свой общий
уровень близости с каталогом, и максимум сырых косинусов выбирал пару с высоким фоном, а не
лучшее совпадение. Теперь косинусы пары стандартизуются по всем 2 103 векторам вида v и
возвращаются на шкалу косинуса запроса: `M + s·(c − mu_wv) / sd_wv`, где M и s — среднее и σ
всей матрицы косинусов запроса. Дальше как было: лучшее окно для вектора, максимум по векторам
slug, top-20. Параметров нет. Счёт кандидата — та же шкала, но у сильного совпадения бывает
выше 1 (до 1,155 на dev). Индекс не менялся: пересборка моделью сервиса дала те же векторы, что
`data/index/visual-s2so400m.npz` (разница 0, другое только `built_at`).

## `s2so400m-vlm35-m2.json` — база цикла улучшений

До 19.09.2026 — модель сервиса по умолчанию. Училась на счётах CV `per_slug="max"`: нынешний
сервис считает `zmax`, с ним она загружается, но получает счёты не той шкалы, на которой
училась, и её цифры ниже к такому сервису не относятся.

Копия `runs/resolve-s2so400m-m2/models/vlm35.json` байт в байт (sha1
`4889680c3ff9c9946661dc95c015d51dcd5ccccb`). Это модель, обученная на всём dev (шаг 2
`bench.train_resolve.run_variant`: сетка L2 групповой 5-fold на всём dev, обучение на всём dev,
температура по out-of-fold счётам этой сетки).

**Что изменилось в полях.** Правила — в [`README.md`](../../README.md) (правила `read_label`):

- таксономия знает цвет и сахар во всех родах и числах («Мускатель белый», «Портвейн красный»,
  «Херес сухой»);
- форма не среднего рода перед словом имени — начало имени, в том числе через перенос строки
  («КРАСНАЯ» / «СТРЕЛКА»); после сорта имя начинают только женский род и множественное число;
- нечёткое кюве на слове цвета или сахара («красные» из «красное») и транслит («ред» из «Red»)
  уходят, а кюве в написании каталога («Блан», «Руж», «Сухой», «Десертный») остаётся рядом с
  цветом и сахаром.

**Что изменилось в признаках** (`resolve-features/3`): цвет — слово названия после стиля
(«Мускатель белый») и в конце названия сорта, если сорт в каталоге встречается с разными
цветами («Мускат белый» / «розовый» / «янтарный»); ищется без правки, в любом роде, кроме
среднего. Версия поднята, поэтому модель на `/2` с этим кодом не загружается, а `-m2` не
загрузится кодом до правки.

Поля этикетки пересобраны этим кодом из тех же чтений: чтения взяты из кэша
`runs/cache-pairs-ocr`, модель зрения не вызывалась.

цифрой называют пару-двойника по обе стороны разбиения («Новый Свет. Пино Нуар» 2018 в test и

Сервис с этой моделью (код до правки родов цвета и сахара) повторял эту
цепочку. Слой выбора сервиса на записанных входах замера (прогоны CV и OCR выше) давал тот же

сервиса (виды `--target none`, top-20, `per_slug=max`), записанные чтения `vlm35`, все 209

| Кадр для CV | CV top-1 | обученный resolve top-1 | top-1 как в замере |
|---|---|---|---|
| в памяти (как стенд), CPU | 151 (72,2 %) | 156 (**74,6 %**) | 209 из 209 |

CPU повторяет записанный GPU-прогон до 5·10⁻⁶ по косинусу, так что расхождение — от файла, а не

## Как переобучить

Модель по умолчанию `-lw-pool` и карта адаптера собираются другим путём —
`research/2026-09-26_fund/final/build_final.py`, по шагам раздела «Подготовка данных и обучение»
корневого [`README.md`](../../README.md#подготовка-данных-и-обучение). Команды ниже — для моделей
прежнего пути (`SVS_CANDIDATE=off`).

Всё на CPU, по готовым прогонам `bench.retrieval --split all` и чтениям в кэше
`runs/cache-pairs-ocr`. Так собрана `-m2`:

```bash
# поля этикетки новым кодом из записанных чтений; без прогрева (он идёт мимо кэша)
python -m bench.ocr_bench --dataset manifest --manifest runs/pairs-ocr/pairs_manifest.tsv \
    --images-dir data/raw/pairs/roskachestvo --gt runs/pairs-ocr/pairs_gt.tsv \
    --ann runs/pairs-ocr/pairs_ann.jsonl --reader vlm:qwen3.5:4b --crop full --crop-px 1024 \
    --split dev --no-warmup --cache-dir runs/cache-pairs-ocr --out runs/ocr-pairs-vlm35-m2
# то же для pairs_phone_manifest.tsv и --images-dir runs/pairs-phone-images → runs/ocr-pairsphone-vlm35-m2
python -m bench.train_resolve \
    --cv runs/cvall-s2so400m-pairs/predictions.jsonl \
    --cv runs/cvall-s2so400m-pairs_phone/predictions.jsonl \
    --ocr vlm35:pairs=runs/ocr-pairs-vlm35-m2/predictions.jsonl \
    --ocr vlm35:pairs_phone=runs/ocr-pairsphone-vlm35-m2/predictions.jsonl \
    --variants vlm35,none --out runs/resolve-s2so400m-m2/
cp runs/resolve-s2so400m-m2/models/vlm35.json configs/resolve/s2so400m-vlm35-m2.json
```

`-goal` собрана так же по прогонам OCR `-m2`, но прогоны CV — с агрегацией сервиса (GPU, по
одному). Индекс пересобран моделью сервиса в
`runs/goal/iter20/index`; его векторы равны `data/index/visual-s2so400m.npz`:

```bash
for Q in pairs pairs_phone; do
  python -m bench.retrieval --queries $Q --index runs/goal/iter20/index/visual-s2so400m.npz --split all \
      --target none --top-k 20 --per-slug zmax --device cuda --dtype float32 \
      --out runs/goal/iter20/cvall-$Q
done
python -m bench.train_resolve \
    --cv runs/goal/iter20/cvall-pairs/predictions.jsonl \
    --cv runs/goal/iter20/cvall-pairs_phone/predictions.jsonl \
    --ocr vlm35:pairs=runs/ocr-pairs-vlm35-m2/predictions.jsonl \
    --ocr vlm35:pairs_phone=runs/ocr-pairsphone-vlm35-m2/predictions.jsonl \
    --variants vlm35 --split dev --folds 5 --top-k 20 --out runs/goal/iter20/resolve
cp runs/goal/iter20/resolve/models/vlm35.json configs/resolve/s2so400m-vlm35-goal.json
```

У `bench.retrieval` по умолчанию `--per-slug max`: без `--per-slug zmax` прогоны CV не те, что
видит сервис.

- Без `--final-test` test не читается. Итоговую модель оценивают на test один раз. Прогоны OCR
  для переобучения собирайте с `--split dev`: обучению строки test не нужны, а с `--split all`
  появляются строки и конверт метрик test для модели, test которой мерить нельзя.
- Пересборка из кэша не должна звать модель зрения. Проверяйте `run.cache` в `metrics.json`:
  `misses` = 0, `hits` = число кадров. Сам `bench.ocr_bench` при промахе кэша читает кадр
  моделью. Поэтому `-m2` собиралась обёрткой, которая на промахе останавливает процесс.
- Модель привязана к индексу, агрегации CV (`CV_PER_SLUG`), top-K, читателю и словарю, на
  которых её учили. Сменили модель CV, индекс или агрегацию — пересоберите прогоны CV. Сменили
  VLM, кроп или бюджет — пересоберите прогоны OCR.
  Поменялся разбор полей (`app/reading/fields.py`, `taxonomy.py`) или смысл признака —
  поднимите `FEATURE_VERSION` (`app/resolve/features.py`), пересоберите прогоны OCR из кэша
  чтений, как выше, и переобучите модель. Иначе старая модель загрузится и тихо получит
  признаки, посчитанные не так, как при её обучении: `provenance` сверяет разметку, словарь и
  читателя, но не разбор полей.
- Сервис не стартует с моделью, у которой `meta.top_k` не равен `SVS_TOP_K`, и с моделью,
  которой нужны чтения двух читателей (например, вариант `both`). Модель другой версии признаков
  не загружается (`ModelFormatError`).
- Имя читателя в признаках (`vlm35.*`) — это ключ, под которым сервис передаёт чтение VLM.
  Модель какой VLM за ним стоит, задаёт `SVS_VLM_MODEL`. Сервис сверяет строку своего читателя
  `vlm@модель|params_hash` (хэш — модель, промпт, размер кадра, `num_predict`, `num_ctx`,
  температура, постобработка) с тем, чьи чтения видела модель. `bench.train_resolve` пишет их в
  `meta.reader_keys` из поля `reader` прогонов OCR. У `s2so400m-vlm35-goal.json` и `-m2` там
  `vlm@qwen3.5:4b|f3a017317f04`. У `s2so400m-vlm35.json` этой записи нет (модель обучена
  раньше), и ключ `vlm35` сверяется с `MEASURED_VLM_READER` = `vlm@qwen3.5:4b|f3a017317f04`
  (`app/api/config.py`) — это строка всех 716 записей `runs/ocr-pairs-vlm35` и
  `runs/ocr-pairsphone-vlm35` (и 298 записей dev их пересборок `-m2`). Расхождение старт не роняет: предупреждение
  в журнале и `provenance.consistent=false` в `/v1/health`, а `run_eval.sh` без
  `--allow-degraded` такой прогон не запустит. Если промпт или параметры `OllamaVlmReader` в коде
  поменяются, упадёт тест `test_default_reader_is_the_one_whose_readings_trained_the_default_model`.
