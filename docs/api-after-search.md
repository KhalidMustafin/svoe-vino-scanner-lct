# Договор API «после поиска»

Договор фиксирует ответы бэкенда (`app/api/after.py`), на которых строится страница продукта
(`app/api/static/index.html`). Источник требований — план функции после поиска (вне репозитория),
§2 «Что строим» и §8 «Право». Поля и имена здесь окончательные на Д1 (24.09): меняются только
вместе с правкой этого файла и заглушек.

Заглушки для вёрстки лежат в `tests/fixtures/after/`. Они собраны на реальных slug каталога
(`data/catalog/wines.jsonl`), а описания в них — нейтральный текст-заглушка: выгрузка организатора
в git не кладётся.

**Без портала (решение 24.09).** Снимок портала (`data/portal/details.json` и `icons/`), 73 карточки
живого портала вне выгрузки и их фото, статус «опубликовано» и сахар из категории живого портала
продукт не использует. Факты карточки — только выгрузка организатора `strapi_output0709.csv`,
`gt_tokens.jsonl` из неё и наш словарь групп вин; блюда, подача и профиль — наши правила (договор
сомелье `docs/api-sommelier.md`). Ниже так и записано; где цифры замерены до этого решения, это
сказано. Заглушки `tests/fixtures/after/` пересобраны под этот состав
(`research/2026-09-24_after/regen_fixtures.py`); карточку без портала показывают и
`wine_card.json`, и `tests/fixtures/somm/wine_card_noportal.json`.

## 0. Что не меняется

`POST /v1/eval/predict` не меняется ни на байт. Его тело — `ScanResult.predict_body()`, то есть
модель ответа без одного поля `evidence` (`app/api/service.py:156`). Любое новое поле модели
`ScanResult` попало бы в ответ скрипту организатора. Поэтому `candidates` и `after` добавляются
только в `scan_body()` (`service.py:165`), а в модели не появляются. Ключи тела predict остаются
прежними: `slug, confidence, margin, top5, outcome, degraded, timings_ms, error`.

## 1. Общие правила

- **Пути только относительные.** `photo_url` — путь нашего сервиса (`/v1/...`).
  Страница работает без интернета. Абсолютных путей машины (`C:\...`) в ответах нет. Поле
  `photo_path` из карточки убрано, путь к файлу остаётся внутри сервиса.
- **Внешняя ссылка одна:** `portal_url = https://vino-svoe.ru/wines/{slug}` — у позиций, чья
  страница опубликована на портале, иначе `null`. Статус публикации — не живой портал, а дамп
  Strapi организатора: карта сайта вин `uploads/wines_sitemap_d778a8e06a.xml` из
  `prod-svoe-vino-strapi.part*.rar` (выгрузка 04.09.2026). В ней 2 037 из 2 103 slug выгрузки;
  66 нет (Союз-Вино, Золотая Балка, черновики вроде `merlo-litavshhuk`) — у них `portal_url: null`.
  Список собирает `scripts/build_portal_links.py` в `app/recommend/portal_links.json`.
- **Право.** В ответах нет цен, слов «купить», «лучший», «вино недели» и эпитетов. В блоках
  рекомендаций (`similar`, `by-label`, `shelf`) нет знака `%`. Процентов похожести нет вовсе,
  а крепость в объяснениях пишется градусами: «Крепость 13,5° против 14°». Все строки
  объяснений проходят `content_filter`. Данных портала (рейтингов, блюд, описаний) в ответах нет.
- **Рекомендации и обычная сортировка.** Все три блока рекомендаций принимают
  `order=reco|plain`, по умолчанию `reco`.
  - При `reco` в ответе есть `notice: "Применяются рекомендательные технологии"`. Страница
    показывает эту плашку и переключатель «Обычная сортировка».
  - При `plain` `notice` равно `null`, `reasons` пусты, а порядок — по названию внутри той же
    категории.
- **Честные фразы.** Если вин меньше трёх или разницы нет, ответ несёт
  `notes: [{code, text}]`. Страница показывает `text` как есть, `code` нужен для тестов.
  Коды описаны в §5–§7.
- **Ошибки.**
  - Неизвестный slug — `404 {"detail": "нет карточки '<slug>'"}`.
  - Неверные `order`, `limit`, `food`, `want` — `422`, стандартное тело FastAPI.
  - `/v1/scan` отвечает `200` всегда, как и сейчас.

### Общие объекты

**Кандидат** (`candidates[]` у `/v1/scan`) — без счётов и вероятностей. `photo_url` равен
`null`, если фото этой позиции на машине нет (как у карточки):

```json
{"slug": "abrau-dyurso-russkoe-igristoe-polusladkoe-shardone-beloe-12",
 "name": "Русское Игристое полусладкое",
 "winery": "Абрау-Дюрсо",
 "photo_url": "/v1/wines/abrau-dyurso-russkoe-igristoe-polusladkoe-shardone-beloe-12/photo"}
```

**Плитка вина** (`items[]` у `similar` и `shelf`, `same_winery[]` и `similar[]` у `by-label`):

| поле | тип | что это |
|---|---|---|
| `slug`, `name`, `winery`, `region` | str | справочные поля каталога |
| `style_label` | str | цвет и сахар по правилам §3: «Красное сухое», «Белое игристое» |
| `sparkling` | bool | игристое |
| `grapes` | list[str] | сорта для показа: «Сира», «Шардоне» |
| `photo_url` | str \| null | `/v1/wines/{slug}/photo`; `null` — фото выгрузки нет или на нём другое вино (§4): страница рисует силуэт |
| `portal_url` | str \| null | `https://vino-svoe.ru/wines/{slug}`; `null` — страницы вина на портале нет (§1) |
| `reasons` | list[str] | объяснение фактами каталога; при `plain` пусто |

У плиток `shelf` есть ещё два поля:
- `dishes` — до трёх блюд `top` правил сочетаний этого вина (`data/somm/pairs.json`, договор
  сомелье, §7.1); нет данных пар — `[]`;
- `want_source` — чем подтверждено направление: `"catalog"` — фактом каталога, `"grape"` — по
  сорту, `null` — направление не выбрано.

**Прочитанное с этикетки** (`after.read` у `/v1/scan`). Этот же объект — тело `by-label`:

| поле | тип | значение |
|---|---|---|
| `winery` | str \| null | винодельня в написании каталога, если чтение сошлось со справочником; иначе как прочитано («CHÂTEAU de CHÂTAIGNIER» — винодельни нет в каталоге); `null` — не прочитана или прочитано только спорное или родовое слово («долина», «шато», «villa») |
| `color` | str \| null | `Белое`, `Красное`, `Розовое`, `Оранжевое` (значения `Color`) |
| `sugar` | str \| null | код `SugarClass`: `brut_nature`, `extra_brut`, `brut`, `suhoe`, `polusuhoe`, `polusladkoe`, `sladkoe` |
| `grapes` | list[str] | коды сортов каталога (`syrah`, `chardonnay`); шум чтения отброшен |
| `abv` | number \| null | крепость с этикетки |
| `sparkling` | bool \| null | `true` — на этикетке признак игристого (класс брют, «игристое», frizzante…); `null` — не понятно. `false` не ставится: отсутствие слова не доказывает, что вино тихое |

## 2. `POST /v1/scan` — дополнения

Вход прежний: multipart с полем `image`. В ответ добавляются два поля, остальное не меняется.

- `card` — тот же объект, что `GET /v1/wines/{slug}` (§3). `null`, если slug нет.
- `candidates` — те же вина, что в `top5`, и в том же порядке. Когда `slug` есть, первый
  кандидат совпадает с ним, а альтернативы — `candidates[1:]`. При отказе
  (`outcome == "out_of_catalog"`) `slug` и `card` равны `null`, но `top5` и кандидаты остаются:
  экран `check` без карточки показывает их все. При ошибке список пуст.
- `after` — подсказка для страницы:

| поле | тип | что это |
|---|---|---|
| `state` | `found` \| `check` \| `not_found` \| `error` | какой экран открыть |
| `reasons` | list[str] | коды причин (таблица ниже) |
| `read` | объект | прочитанное с этикетки (§1) |
| `read_label` | str \| null | готовая строка для «Прочитали на этикетке: …»: «Фанагория · игристое · оранжевое · брют · 12 % об.»; `null` — ничего не прочитано |
| `winery_in_catalog` | bool \| null | `true` — прочитанная винодельня есть в каталоге; `false` — винодельня прочитана, но её в каталоге нет; `null` — не прочитана или не узнана |
| `winery_slugs` | list[str] | канонические вина этой винодельни из пула (§5), по названию; `[]`, если её нет в каталоге |
| `suggest_not_found` | bool | Д3: `true` — счёт CV лучшей серии ниже порога, «похоже, этой бутылки может не быть в каталоге». Есть в ответе всегда, по умолчанию `false`. Правило ниже |
| `question` | object \| null | сомелье: один вопрос экрана `check` по полю, которым различаются варианты, — `{field, text, options: [{label, slug}]}`; не `check` или различать нечем — `null`. Правило и тексты — договор сомелье `docs/api-sommelier.md`, §5 |

`read_label` — дополнение к §2 плана, чтобы страница не собирала подписи сама. `question` —
дополнение 24.09; как и остальное `after`, в `/v1/eval/predict` оно не попадает.

**Как выбирается `read.winery`** (реализация, 24.09; правки 25.09). Чтение отдаёт несколько
написаний: полную форму словаря и отдельные токены. В счёт идут только однозначные написания:
имя винодельни каталога целиком (в том числе из родовых слов, как «Кубань-Вино») или
написание ровно одной винодельни. Родовое слово («шато», «chateau», «villa», «domaine»,
«долина») и слово нескольких виноделен винодельню не называют. По порядку берётся:
1. винодельня одного из кандидатов `top5` (по рангу), если её однозначное написание прочитано.
   Родовой токен винодельню кандидата не подтверждает: до правки «chateau» на этикетке
   Château de Châtaignier «находил» Château Le Grand Vostock из top-5;
2. винодельня, названная в строках VLM словом хозяйства («CHÂTEAU» / «de CHÂTAIGNIER»,
   «Muzaradi Winery», «DOMAINE RENAUD»), если она не похожа ни на одну винодельню каталога
   (скелет с одной-двумя правками: «ВИНОДЕЛЬНЯ МЕЙСХАКО» — это Мысхако). Тогда `winery` —
   строка как прочитана, а `winery_in_catalog: false`. Словарь каталога знает только винодельни
   каталога, поэтому чужая винодельня видна лишь в строках;
3. написание, совпадающее с именем винодельни каталога целиком;
4. написание, которое указывает ровно на одну винодельню.

Спорное слово винодельней не считается (`winery: null`). На 353 кадрах поля v2 в каталоге
(прогон `pfix_final`) прочитанная винодельня совпала с винодельней правильного вина в 280
случаях, в 48 не прочитана, в 25 прочитана другая — чаще всего «Усадьба Маркотх»: Маркотх —
ещё и хребет, его пишут на этикетках Мысхако и Шато Пино. `winery_in_catalog: false` на этих
кадрах не выпадает ни разу. На 409 кадрах вне каталога ложных «винодельня в каталоге» стало 28
вместо 45, `false` — у 24 кадров, из них неверно у одного (Chateau Alvisa прочитан как
«CHATEAU ALLIANCE»). Подробности — `research/2026-09-24_after/hint.md`.

**Правило `state` на Д1.** Порог `AMBIGUOUS_P_TOP1 = 0.5` взят из `service.py:101`. Правила
проверяются сверху вниз, срабатывает первое подошедшее:

| условие | `state` | `reasons` |
|---|---|---|
| `outcome == "error"` | `error` | префикс `error` до двоеточия: `no_image`, `bad_request`, `too_large`, `decode`, `cv`, `not_ready`, `internal` |
| `outcome == "out_of_catalog"` (правило отказа при `SVS_ABSTAIN=ooc_only`) | `check` | `abstain` |
| `confidence.top1 == null` (resolve упал или читатель ничего не прочитал — ответ дал CV, Э2) | `check` | `no_confidence` |
| `outcome == "ambiguous"` (p_top1 < 0,5) | `check` | `ambiguous` |
| `confidence.top1 < 0.5` | `check` | `low_confidence` |
| иначе | `found` | `[]` |

`not_found` сервер не возвращает — это итог калибровки Д2 (план §3 п. 6,
`research/2026-09-24_after/hint.md`). Правило проверено на записанных ответах поля:
- винодельня каталога прочитана однозначно, её названия не условные, и каждая её позиция
  спорит с этикеткой по сахару, цвету или сортам (`winery_no_match`), или винодельня
  названа словом хозяйства и её в каталоге нет (`winery_not_in_catalog`);
- счёт CV лучшей серии (zmax) ниже порога.

При пороге 0,8543 ложных `not_found` на 353 кадрах каталога 7, а полнота на 409 кадрах вне
каталога — 19,3 % (79). Без порога она не выше 20,3 %: мешает чтение, а не порог. По плану
при полноте ниже 50 % автоэкрана нет. Экран `not_found` открывает кнопка «Моего вина здесь нет»:
страница шлёт `after.read` в `POST /v1/similar/by-label`. Правило в коде есть и выключено
(`after_layer.NOT_FOUND_VISUAL_MAX = None`); `calibrate_hint.py` повторяет замер на новом
прогоне. Если его включат, `slug` и `card` останутся: predict не меняется. Заглушка
`scan_not_found.json` показывает такой ответ.

**Подсказка `suggest_not_found` (Д3).** Считается после правила выше, по одному ответу сканера:
- `suggest_not_found = true`, когда счёт CV лучшей серии (zmax, `evidence.abstain.best_visual`;
  нет его — счёт CV top-1) ниже `after_layer.SUGGEST_NOT_FOUND_VISUAL_MAX = 0.8024`;
- тогда `found` становится `check`, а к `reasons` любого экрана, кроме `error`, добавляется
  код `visual_low`: `["visual_low"]`, `["ambiguous", "visual_low"]`, `["abstain", "visual_low"]`;
- `not_found` подсказка не открывает никогда. `slug`, `card`, `top5` и `candidates` остаются,
  тело `/v1/eval/predict` не меняется ни на байт. Скрипт организатора читает только top-1
  predict, поэтому на его счёт подсказка не влияет;
- при `error` флаг всегда `false`.

Порог откалиброван на записанных ответах поля (`research/2026-09-24_after/hint.md`, раздел
«Подсказка suggest_not_found»). Правило калибровки — наибольший порог, при котором флаг стоит не
больше чем на 7 из 353 кадров каталога. Результат:
- на каталоге флаг стоит на 6 из 353. `found` → `check` на 4 кадрах, и все четыре сервис
  угадал — это цена подсказки;
- на 409 кадрах вне каталога флаг ловит 263 (64,3 %);
- вне выборки (5 фолдов по винам) — медиана 8 ложных из 353 и полнота 58,2 %.

**Путь по умолчанию (кандидат 2, карта `adapter-lw`) — своя шкала счёта.** Порог там не 0,8024, а
`SUGGEST_NOT_FOUND_VISUAL_MAX_BY_ADAPTER` = 0,4379 (`app/api/config.py`; в мете файла карты —
прежние 0,4299). Правило то же — наибольший порог, при котором флаг стоит не больше чем на 2 %
кадров каталога по выдаче карты вне фолда, — но кадры каталога — v2 353, kr-dev 308 и
R-оригиналы 65 вместе: флаг на 14 из 726 (`research/2026-09-26_ooc/suggest_calibration.json`).
Вне каталога флаг ловит 236 из 408 кадров ooc_v2 (57,8 %) и 286 из 600 студийных снимков
krasnostop.ru вне каталога (47,7 %). Действующий порог — в `/v1/health`,
`model.suggest_not_found_visual_max`.

Полностью ответ — `scan_suggest.json`: кадр R086, Bel Colle Barolo, которого нет в каталоге.
Сканер отдал чужое вино с p = 0,68, счёт CV — 0,69.

`evidence.abstain` пишется всегда (с 24.09; раньше — только при `SVS_ABSTAIN=ooc_only`). При

`no_position_matches`, `conditional_names`, `below_floor`. Правило подсказки берёт из него
`best_visual` (счёт CV лучшей серии), а спор фактов считает само: условие S10
`no_position_matches` — про совпадение текста, и на поле оно ловит меньше (13,5 % против
19,3 % при тех же 7 ложных). Сбой проверки при `off` флага в `degraded` не ставит:
`degraded` уходит в predict.

## 3. `GET /v1/wines/{slug}` — карточка

Карточка открыта для любого slug выгрузки организатора (2 103 позиции). Любой другой slug — 404,
в том числе 73 карточки живого портала вне выгрузки: после решения 24.09 их в продукте нет. Все
поля — из выгрузки (через `gt_tokens.jsonl`) и наших правил; снимок портала не читается.

| поле | тип | источник |
|---|---|---|
| `slug`, `name`, `winery`, `region` | str | выгрузка: `Slug`, «Название вина», «Винодельня», «Регион» |
| `grapes` | list[str] | «Сорт винограда» выгрузки, как записано (с заглушками вроде «Белые сорта винограда») |
| `category` | str | «Категория» выгрузки — цвет |
| `color` | str | «Цвет» выгрузки — оттенок: «Рубиновый»; `""` — не заполнен |
| `color_label` | str | то же, что `category`: `Белое`, `Красное`, `Розовое`, `Оранжевое` |
| `sugar_class` | str \| null | код `SugarClass` по правилу сахара ниже; `null` — неизвестен |
| `sugar`, `sugar_label` | str | сахар словом: «сухое», «брют»; `""` — неизвестен |
| `sparkling` | bool | правило игристости ниже; `false` — «не отмечено» |
| `style_label` | str | цвет и сахар: «Красное сухое»; сахар неизвестен — «Белое игристое» у игристого, иначе один цвет |
| `description` | str | «Описание» выгрузки как есть (только края без пробелов); нет — `""` |
| `description_src` | `catalog` \| null | `catalog` — описание из выгрузки; `null` — описания нет |
| `photo_name` | str | «Название фото» выгрузки |
| `photo_url` | str \| null | `/v1/wines/{slug}/photo`; `null` — фото выгрузки нет или на нём другое вино (§4) |
| `portal_url` | str \| null | `https://vino-svoe.ru/wines/{slug}`; `null` — страницы на портале нет (66 из 2 103, §1) |
| `alcohol` | number \| null | крепость, % об., из slug выгрузки (правило ниже) |
| `alcohol_max` | number \| null | верх диапазона: «11–13» в slug → `11`, `13` |
| `alcohol_src` | `catalog` \| null | `catalog` — крепость из slug; `null` — неизвестна |

**Правило сахара** — только то, что написал организатор, по порядку:
1. класс сахара, названный в «Название вина» (`scripts/build_gt_tokens.py`, `ru_sugar`: «Brut Zero
   Dosage» — брют натюр, «экстра брют» поглощает «брют»); «сухое» и «сладкое» — только целым словом:
   опечатка выгрузки «Абрау Купаж красный полсусладкое» — не «сладкое», сахар берётся из slug
   (`polusladkoe`);
2. последнее слово сахара в slug: `ekstra-bryut`, `bryut-natyur`, `polusladkoe`, `polusuhoe`,
   `sladkoe`, `suhoe`, `bryut`, `brut` («…-igristoe-sladkoe-krasnoe-bryut-125» — брют: хвост slug
   «цвет-сахар-крепость» пишет категорию организатора);
3. иначе `null`.

Замер 24.09: сахар известен у 1 727 из 2 103 позиций и у всех совпадает с прежним сахаром живого
портала; у 376 его нет ни в названии, ни в slug. Прежний `fields.sugar.class` из `gt_tokens.jsonl`
для карточки не годится: у 2 013 позиций он взят из категории живого портала (`src: live_api`).
Распознавание (`app/resolve`) по-прежнему читает `gt_tokens.jsonl` как есть — это не показ.

**Правило игристости:** `true`, если сахар из брют-семейства (`brut`, `extra_brut`, `brut_nature`)
или в названии либо slug есть слово игристого — те же слова, что у `after_layer._SPARKLING_WORDS`,
и транслит `igrist`, `shampansk`. Пет-нат — в любом написании: «Петнат», «Пет-Нат», «Пет Нат», в
slug и `pet_nat` через подчёркивание (`denisov_pet_nat_rubin`). Иначе `false`. Замер: 297 из 2 103
(с живым порталом было 347).

**Правило крепости:** `fields.abv.value` из `gt_tokens.jsonl` (разобрано из slug): одно число —
`alcohol`; два — `alcohol` меньшее, `alcohol_max` большее; вне 3–25 — `null`. Целое число, равное
двум последним цифрам года урожая позиции (`fields.year.value`), — год, а не крепость: у `daniel-22`
(«Daniel, 2022») крепости нет, а не «22 % об.» (`catalog.slug_abv`). Известна у 1 567 из 2 103,
диапазонов 32. Разметку `gt_tokens.jsonl` правило не трогает: её читает распознавание.

**Что ушло из карточки.** `dishes`, `temperature`, `category_gradient` (снимок портала),
`live_category` и `published` (живой портал) в ответе больше нет. Им на смену:
- блюда «к чему подать» с чипами правил, подача по нашей таблице и профиль вкуса — `GET
  /v1/wines/{slug}/sommelier` (договор сомелье, §2);
- фон шапки — токен страницы по `color_label` (`--g-red`, `--g-white`, `--g-rose`, `--g-orange`;
  договор сомелье, §8.2), а не поле ответа.

Прежние поля `category`, `color`, `sugar`, `sugar_class` и `photo_name` остаются: на них опирается
полевой стенд; `sugar` и `sugar_class` теперь по правилу сахара выше. Поле `photo_path` убрано.

## 5. `GET /v1/wines/{slug}/similar?limit=3&order=reco|plain`

«Похожие из других виноделен». `limit` — от 1 до 12, по умолчанию 3.

- **`reco`** — ранжирование фактами каталога (`app/recommend/facts.py`).
  - Отбрасываются вина той же винодельни, той же группы `wine_id` и всё вне пула.
  - **Пул** (решение 24.09) — канонические позиции выгрузки (каноническая позиция группы — наш
    словарь `wine_groups.json`) с фото выгрузки (§4): 1 980 вин, из них 17 — с фото чужой бутылки
    (`photo_url: null`, плитка с силуэтом). Статус «опубликовано» и 73 живые
    карточки портала в пул не входят. Если канонической позицией группы в словаре была живая
    карточка портала, её место занимает позиция выгрузки той же группы, лучше — с показанным фото: так в пул
    возвращается `merlo-litavshhuk` (группа `W1364`). Факты — по правилам §3: у 376 позиций сахар неизвестен, и
    неизвестный сахар подбор не сужает (`facts.sugar_close`).
  - Остаются вина того же цвета и игристости, сахар — в пределах одной ступени.
  - Ключ сортировки: мера Жаккара по сортам → тот же сахар → разница крепости → регион → slug.

## 6. `POST /v1/similar/by-label?limit=3&order=reco|plain`

Экран «Не тупик»: «этой позиции нет, но винодельня в каталоге есть». Тело запроса — объект
`read` (§1). Все поля необязательны; страница шлёт `after.read` как есть.

```json
{"winery": "Фанагория", "color": "Оранжевое", "sugar": "brut", "grapes": [], "abv": 12,
 "sparkling": true}
```

**`exclude`** (Д3, необязательно) — массив slug, которых в выдаче быть не должно:
`{...after.read, "exclude": ["<slug>", ...]}`. Страница шлёт сюда то, что человек видел в этом
скане и отверг кнопкой «Моего вина здесь нет», в порядке показа и не больше 20:
- самое похожее — вино карточки скана (top-1);
- варианты «Не то вино?» — только если список раскрывали. При `check` он раскрыт сразу, кроме
  подсказки `suggest_not_found` с карточкой; при `found` и при подсказке он свёрнут. Нераскрытые
  варианты не исключаются: среди них может быть вино человека;
- карточки, открытые из вариантов.

Правила сервиса:
- Исключаются сами slug и **каждый slug их группы `wine_id`** (`wine_groups.json`): отвергнутое
  вино не вернётся тем же вином в другом объёме или году.
- Исключение действует и на `same_winery`, и на `similar`. Оно применяется до подбора, поэтому
  места в выдаче добираются следующими винами, и правило «одна винодельня — одно место» не
  нарушается.
- Неизвестные slug пропускаются молча.
- Больше 20 элементов, не массив строк (в том числе `null`) или строка длиннее 200 символов —
  `422`.
- Поля нет или массив пуст — ответ тот же, что без него, байт в байт (заглушка `by_label.json`
  собрана без `exclude` и не изменилась).
- В ответ `exclude` не возвращается, эхо `read` прежнее.
- `winery.count` и регион винодельни считаются по всему справочнику.
- Фраза `relaxed_color` говорит о каталоге: исключённые вина в нём есть. Если исключено
  единственное оранжевое вино, ответ — «…в каталоге мало — добавили…», а не «…нет…».

Ответ:

- **`winery`** — `{name, in_catalog, count}`. Вина берутся через
  `CatalogAttrs.slugs_of_winery` (`app/resolve/attrs.py:259`).
- **`same_winery`** — до 6 вин этой винодельни.
  - `reco`: сначала совпавшие по игристости, цвету и сахару.
  - `plain`: по названию.
  - Пусто, если винодельни нет в каталоге.
- **`similar`** — до `limit` вин других виноделен, близких по прочитанным фактам. Ранжирование
  то же, что у `/similar`. Регион этикетка не даёт — берётся самый частый регион вин этой
  винодельни в каталоге. Игристость не прочитана — брют-семейство сахара ставит её в `true`,
  иначе первыми идут тихие вина.
- **`same_winery`** в `reco` объясняется сортами, сахаром и цветом (регион и крепость у
  винодельни общие); нечем объяснить — «Та же винодельня».
- **`read`** — нормализованное эхо запроса. `read_label` здесь нет: в нём крепость
  со знаком `%`, а в блоке рекомендаций этого знака быть не должно. Строку «Прочитали: …»
  страница берёт из `after.read_label` ответа `/v1/scan`.
- **`notes`** — коды:
  - `relaxed_color` — вин такого цвета с такой игристостью меньше `limit`, цвет ослаблен
    («…в каталоге нет — показываем…» или «…в каталоге мало — добавили…»);
  - `winery_unknown` — винодельни каталога нет:
    - «Этой винодельни в каталоге нет» — прислано написание, и винодельни в каталоге нет;
    - «По прочитанному названию винодельню однозначно не определить» — прислано спорное слово;
    - «Винодельню по этикетке определить не удалось» — винодельни в теле нет, а цвет, сахар,

  - `no_facts` — цвет, сахар, сорт и игристость не прочитаны: `similar` пуст, подбирать не по

  - `fewer_than_three` — нашлось меньше трёх.
- Неверные типы в теле (`abv: "крепкое"`, `grapes: "merlot"`, `exclude: "slug"`) и

## 7. `GET /v1/wines/{slug}/shelf?food=meat|fish|cheese|none&want=fresher|softer|sweeter|none&order=reco|plain`

«Сомелье у полки» (`app/recommend/shelf.py`, реализация Д2, 25.09). От пользователя приходят
только значения чипов; по умолчанию `food=none`, `want=none`, `order=reco`. Любое другое
значение — `422`, неизвестный slug — `404`.

**Чип «К чему?» (`food`).** После решения 24.09 — по нашим правилам сочетаний, а не по блюдам
портала. Вино подходит чипу, если хотя бы одна его пара с блюдом группы `food` имеет вердикт `yes`
(`data/somm/pairs.json` и группы `food` в `dishes.json`, договор сомелье, §7.1–7.2):

| `food` | подпись чипа | блюда правил сочетаний |
|---|---|---|
| `meat` | «Мясо» | категория `main_meat` (шашлыки, стейк, плов, гуляш…), а также буженина, пастрома, холодец |
| `fish` | «Рыба» | категории `seafood` и `seafood_raw`, а также малосольная сёмга, солёная сельдь, копчёная скумбрия, икра, блины с икрой, селёдка под шубой, уха, суши и роллы |
| `cheese` | «Сыр» | сырная тарелка |
| `none` | «Без разницы» | блюда не фильтруются |

Птица (`main_poultry`) в «Мясо» не входит — как в плане. Сколько вин попадает под каждый чип,
считает сборка `scripts/build_somm.py`; прежние цифры снимка 23.09 (рыба 1014, мясо 919, сыр 1180)
к новому правилу не относятся. Нет данных пар — при `food ≠ none` выдача пуста с нотой `no_pairs`
«Подбор к блюдам недоступен: нет данных правил сочетаний».

**Чип «Какое хочется?» (`want`).** Задаёт направление. Сдвиг подтверждается фактом каталога
(`want_source: "catalog"`) или осью профиля «по сорту» (`want_source: "grape"`, в объяснении —
пометка «по сорту»). Профиль — перенос `build_profile` «Лозы» (`app/recommend/build.py`).

| `want` | подпись чипа | каталог | по сорту |
|---|---|---|---|
| `fresher` | «Посвежее» | сахар ниже; крепость ниже на 0,5° и больше | кислотность выше |
| `softer` | «Помягче» | сахар на ступень выше, но не слаще полусухого (сухое → полусухое, экстра брют → брют) | танины ниже у красного и оранжевого, кислотность ниже у белого и розового; сахар — не выше потолка (см. ниже) |
| `sweeter` | «Послаще» | сахар выше | — |
| `none` | «Без разницы» | направление не выбрано, сахар в пределах ступени | — |

- Ось «по сорту» считается, только если профили обоих вин опираются на сорт, сорта разные и
  разница не меньше 0,3 (порог зонда «Лозы»).
- Против направления нельзя идти ни по одному признаку: «посвежее» не бывает слаще и крепче
  на 0,5° и больше; «помягче» не бывает суше; по сорту ни то ни другое не уходит в обратную
  сторону на 0,3 и больше.
- «Помягче» никогда не становится «послаще» (решение 24.09). Потолок сахара — полусухое, а у
  вина слаще полусухого — его собственный сахар; у вина без сахара — полусухое. Вино с
  известным сахаром выше потолка не идёт ни по каталогу, ни по сорту, даже с танинами ниже.
  Итог:
  - сухому, брют и экстра брют — ступень сахара вверх, но не выше полусухого, или вина
    мягче по сорту не слаще полусухого;
  - полусухому — только полусухие, мягче по сорту;
  - полусладкому и сладкому — только вина того же сахара, мягче по сорту: ступень вверх для
    них уже «послаще».

  Неизвестный сахар кандидата потолок не проверяет. После решения 24.09 сахар неизвестен у 376
  позиций выгрузки (§3), поэтому «помягче» может предложить вино без сахара — такое вино
  объясняется только «по сорту».
- Вино, подтверждённое и каталогом, и сортом, идёт первым; затем только каталогом; затем только
  сортом. `want_source` плитки — `"catalog"`, если есть факт каталога, иначе `"grape"`.

**Пул.** Тот же пул, что у похожих (§5, 1 980 вин). Своя винодельня и своя группа `wine_id`
исключены. Сначала берутся 60 ближайших по фактам среди вин того же цвета и игристости, у
которых есть блюдо чипа и сдвиг в нужную сторону. Ключ близости: мера Жаккара по сортам →
разница сахара в ступенях →
разница крепости → регион → slug. Если таких вин меньше трёх, берётся весь пул; вина того же
стиля остаются первыми. `pool: "catalog"` и нота `pool_expanded` — только если расширение
добавило в выдачу вино другого цвета или игристости; иначе `pool: "near"`. Одна винодельня —
одно место.

**Плитка.** Общая плитка (§1) и ещё два поля:
- `dishes` — до трёх блюд `top` правил сочетаний этого вина (`pairs.json`); нет данных — `[]`;
- `want_source` — `"catalog"`, `"grape"` или `null` (при `want=none` и при `plain`).

`reasons` — не больше четырёх строк, по порядку:
1. блюдо: «К мясу — по правилам сочетаний», «К рыбе и морепродуктам — по правилам сочетаний»,
   «К сырам — по правилам сочетаний»;
2. направление: «Посвежее: крепость 11,7° против 16°», «Помягче: полусухое, а не сухое»,
   «Помягче по сорту: танины ниже — Мерло, а не Сира»;
3. другой цвет, если вино из расширенного пула: «Белое, а не красное»;
4. факты карточки, как у похожих, без повтора того, что уже названо: сорта, сахар, регион,
   крепость.

**Ответ.** 3 вина или честная фраза. Коды `notes`:

| код | текст |
|---|---|
| `pool_expanded` | «Среди близких по стилю не нашлось — подобрали из всего каталога» |
| `not_evaluable` | направление не оценить: у самого вина нет признака, от которого считается сдвиг (`shelf.direction_evaluable`). «Послаще» без сахара — «Сахар этого вина в каталоге не указан — послаще подобрать не по чему»; «помягче» без сахара и без оси «по сорту» — «Сахар этого вина в каталоге не указан, а по сорту мягкость не оценить — помягче подобрать не по чему» (сахар есть, но выше полусухого — «По сорту мягкость этого вина не оценить — помягче подобрать не по чему»); «посвежее» без сахара, крепости и оси «по сорту» — «Сахар и крепость этого вина в каталоге не указаны, а по сорту свежесть не оценить — посвежее подобрать не по чему». Это не «разницы нет»: сравнивать не с чем. Вин нет, других нот нет |
| `no_difference` | ни одно вино пула не сдвинуто в нужную сторону, даже без учёта блюда: «послаще» сладкому — «Это вино уже сладкое: послаще в каталоге по описаниям не найти»; иначе «По описаниям разницы нет — помягче в каталоге не найти» (с тем же словом направления: посвежее, помягче, послаще) |
| `fewer_than_three` | направление в каталоге есть, но с этим блюдом вин меньше трёх: «Нашлось меньше трёх»; ни одного — «К рыбе посвежее в каталоге не нашлось» |
| `no_pairs` | `food ≠ none`, а данных правил сочетаний нет: «Подбор к блюдам недоступен: нет данных правил сочетаний» |

## 9. Данные и право

- **Откуда поля карточки** (решение 24.09). Только выгрузка организатора
  `strapi_output0709.csv` — через `gt_tokens.jsonl` и по правилам §3 — и её фото (§4). Блюда,
  подача и профиль — наши правила (`data/somm/`, договор сомелье, §7). Снимок портала
  `data/portal/` сервис не читает, а `deploy/pack_data.sh` каталог `portal/` в пачку не кладёт.
- **Справочник для рекомендаций** — позиции выгрузки (строки `in_csv` из
  `data/catalog/wines.jsonl`) и `wine_groups.json`. Из `wines.jsonl` берутся только наша
  группировка (`wine_id`, `canonical`, `is_canonical`, `winery_norm`) и коды сортов из выгрузки;
  цвет, сахар, игристость, крепость, «опубликовано», `category_live`, `photo` живого портала и
  73 строки вне выгрузки не используются.
- **Что не попадает в git.** Фото карточек `data/catalog/photos_small/`, снимок портала
  `data/portal/`, комплект `*-live71` и CSV выгрузки организатора; остальная пачка `data/` лежит в git
  (`data/README.md`). Кроме того, в git
  нет join CSV «Лозы» (`loza_id`, `expert_score`, `price_rub`), данных Роскачества и корпуса статей.
- `publicRating` и остальные данные портала не показываются и в сортировке не участвуют.
- **Где сервис ищет данные слоя** (по умолчанию — от `SVS_DATA_DIR`): `SVS_WINES_PATH`
  (`catalog/wines.jsonl`, рядом `wine_groups.json`), `SVS_SOMM_DIR` (`somm/`: пары, блюда,
  подача, словарь, справочник), `SVS_PHOTO_DIR` (лёгкие фото `<slug>.webp`, по умолчанию
  `catalog/photos_small`, на полевом VPS — `SVS_FIELD_PHOTO_DIR`). `SVS_PORTAL_DIR` больше не
  читается. Нет файлов — сервис стартует: карточки из разметки, похожих нет, а
  `/v1/health.after` и `/v1/health.somm` показывают, что загружено.
- **Кадры не пишутся.** Полевой контур (`/v1/field/*` и страница стенда `/field`) регистрируется
  только при `SVS_FIELD=1`; продукту он не нужен.
- **Страница продукта и стенд.**
  - `GET /` — страница продукта `app/api/static/index.html`, открыта всегда, без флага и ключа
    (`register_page_routes`, `app/api/page.py:76-96`). Под `/static` — только шрифт, картинки
    оформления и лист сомелье `somm.js` и `somm.css`; HTML оттуда не отдаётся. Тип файла задан
    таблицей `ASSET_TYPES` (`app/api/page.py:36-47`): `.woff2` уходит как `font/woff2`, а не
    `application/octet-stream`, `.js` и `.css` — с кодировкой `utf-8`.
    Шрифт заголовков — Playfair Display 500 (OFL), три подмножества woff2 в
    `app/api/static/fonts/`, лицензия `OFL.txt` рядом и наружу не отдаётся.
  - `GET /field` — страница полевого стенда, только при `SVS_FIELD=1`
    (`app/api/main.py:307-311`). Ключ `SVS_FIELD_TOKEN` закрывает `/field` и `/v1/field/*`.
  - Старая ссылка стенда `/?k=…` при включённом контуре — 307 на `/field?k=…` со всеми
    параметрами (`app/api/page.py:87-88`); без контура это просто страница продукта.
